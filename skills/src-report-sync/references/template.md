## 手工撰写纪律（A–D，最高优先级）

2026-09-21 十二段实验失败回退的核心教训：

- **A** 每份 vault 文件必须先逐字读取对应源报告正文，再按五段模板手工组织撰写；内容从源报告忠实搬运不压缩（漏洞描述、危害事实全量保留，涉及接口与数据包逐条对应），但文风一律改写为第三人称书面报告体（2026-09-22 用户定论，存量文件待批量刷）。
- **B** 禁止用正则或脚本自动抽取字段拼装生成 vault 正文；python 脚本只允许做 hash 计算、manifest 读写、批量校验与长 token 提取比对，不允许生成正文内容。
- **C** 数据包整段原样内嵌于步骤下方：HTTP 请求块保留源报告全部内容（含鉴权头与 Content-Type），长 token 值用脚本从源文件提取替换并逐字节比对，禁止手工转录；表格必须含 `|---|` 分隔行；http 代码块的闭合符号独立成行。响应块与请求块成对：响应内容从源报告回包段或任务根 dig 原始留存逐字节搬运，含状态行、留存全部响应头与响应体，不虚构状态码、响应头或响应体；留存仅部分字段时有什么写什么，缺失部分如实标注；长响应体超约 40 行截断并标注截取范围；源报告回包段更新（如重放后）时 vault 同步搬运并复核样例与鉴权值一致（2026-09-29 用户要求确立）。
- **D** 每份新写/改写文件落盘前自检：五段标题齐全、无十二段残留标题、frontmatter 字段齐全、表格与代码块格式正确。

## 落盘自检清单（纪律 D 的执行表）

- [ ] 五段标题齐全：漏洞名称/漏洞描述/危害/利用方式/修复方法 + 备注
- [ ] 无十二段残留标题（## 漏洞标题/## 子类型/## 影响软件系统/## 验证过程/## 安全影响/## 复现步骤/## 漏洞危害/## 修复建议/## 复测建议）
- [ ] frontmatter 八字段齐全（非 Ntcert 为七字段：无来源）+ tags 缩进正确
- [ ] 每个 http 块：请求行完整、头部含 Content-Type（有 body 时）、闭合 ``` 独立成行、块末行后有换行
- [ ] 每个请求块之后跟对应响应块，或一行「（该请求的原始响应未留存…）」括注，无悬空请求块（2026-09-29 起）
- [ ] 含长 token 的块：已用脚本提取替换并逐字节比对通过
- [ ] 表格（如有）含 |---| 分隔行
- [ ] 文风：无破折号、无标签冒号、无「不是而是/值得注意的是」、无空词、无第一人称复盘与口语词（我没登录/我拿到了/等于证明/打一遍/抄出来等，2026-09-22 用户定论）
- [ ] 文中不做网络请求、不执行命令（纯文本搬运）

## 成品基准（活指针，不内嵌示例）

动笔前先 Read vault 内一份按现行规范落盘的近期收录件，作为格式、文风与请求/响应块形态的完整基准。基准件选取标准：frontmatter 字段齐全、五段齐全、请求块与响应块成对（或带未留存括注）、通过当轮文风校验；可按 manifest 最近 imported 条目的 `vault_file` 定位，或取 vault 内 mtime 最新的收录件。

本 skill 不内嵌静态示例：规则演进后内嵌件必然过时（历史教训：内嵌示例曾停留在无响应块的旧形态，与现行规则脱节），一律以 vault 活件与 manifest rules 现文为准。
