# 整理规则全文（通用正源 · 2026-09-30 版）

> 本文件是整理规则的**正源**（通用方法论，2026-09-30 起正源由 manifest 翻转至此，正文不含具体客户与目标信息）。manifest 的 `rules` 字段是本文件条文的实例化缓存：条文主体与本文件一致，另带本机判例增补（具体对象名溯源）。每轮开工仍必须先读 manifest rules 拿增补；条文主体冲突以本文件为准并当轮修正 manifest。修订流程：改本文件 → 同步 manifest 保持条文主体一致；新判例事件只追加于 manifest 侧。本机路径与来源分区实例见 SKILL.md「本机部署配置」。
## 1. 布局

一个单位一个文件夹，一个漏洞一个文件，MOC 为 vault 根 `SRC报告/00-总览.md`（2026-09-22 用户指令由 `2026-SRC/00-总览.md` 上移，涵盖 `2026-SRC/` 与 `ET-Pentest/` 两棵树并按实际目录分区）；跨年按当前年份建 `202X-SRC`；带来源线的漏洞在年份目录下先过来源分区层级再按单位分夹（见第 15 条）。

操作要点：vault 根的 `00-总览.md` 不算漏洞文件；当前实际布局 `2026-SRC/{SRC,来源分区…}/` + `ET-Pentest/<单位>/`（个别手工单位历史上落在来源分区内），手工件落位以 manifest `vault_file` 为准。

## 2. 单位归并

以报告正文载明的单位为准，目录名仅作线索；正文未载明的以平台名暂代。

操作要点：正文只写平台名时，frontmatter 单位字段可写「平台名（报告未载明运营主体，以平台名归档）」；后续补正运营主体时改目录名并迁 manifest（判例：某餐饮油烟监管平台、某景区均由平台名补正）。单位名可带括号补系统名区分，如「某市机关事务管理局（某后勤管理平台）」。

## 3. 收录标准

正文描述了具体漏洞且附验证证据；结论性/过程性文档判 no-vuln 不收录；安全设备公网直暴（防火墙/VPN/VDI/堡垒机等设备管理面公网可访问类发现）判 excluded 不收录不进漏洞清单（2026-09-11 用户定论，设备上未授权读到数据如路由表/会话/账密/流地址的仍正常收录）。

操作要点：设备面与设备数据面的分界线。H3C 防火墙管理面直暴=excluded；同设备匿名读到路由表=正常收录。

## 4. 去重

同一漏洞多版本（CNVD材料、docx/pdf 导出件、汇总稿）只收信息最全的正式版，其余记 duplicate；docx/pdf 同目录存在同名 md 时直接按导出件跳过，无同名 md 时解析一次再判定。

操作要点：duplicate 条目不带 vault_file；note 写明与哪条重复（如「与既有 PbootCMS 表单留言同接口」）。

## 5. 模板

YAML frontmatter（单位/资产/风险等级/漏洞类型/首次收录/源报告/tags）+ 五段正文（漏洞名称/漏洞描述/危害/利用方式/修复方法）+ 备注（手工批注区，冲突保护对象）。利用方式中数据包完整内嵌步骤下方。内容从源报告忠实搬运不压缩；漏洞描述/危害改写为正式书面报告文风（第三人称客观陈述，禁止第一人称复盘口吻与口语词，利用方式步骤说明同步书面化，2026-09-22 用户定论；存量已于 2026-09-23 全量刷毕并回写基线）。2026-09-21 十二段实验回退，统一五段。正文必须由模型逐字读源报告后手工撰写，禁止正则/脚本抽取字段拼装生成（十二段实验失败根因，2026-09-21 回退时确立）；python 脚本仅限 hash 计算、manifest 读写、批量校验、长 token 提取与逐字节比对，不允许生成正文内容。落盘前自检：五段标题齐全、无十二段残留标题、表格含 |---| 分隔行、http 代码块闭合符号独立成行。

操作要点：细节模板与成品基准见 `template.md`。带来源线的另按第 15 条加来源字段。

## 6. 修复方法缺失

代写并标注（整理补充）。

## 7. 文风

去 AI 味；事实全部来自源报告；不用破折号、不用标签冒号、不用「不是而是/值得注意的是」类句式；正文一律第三人称客观书面语，禁「我没登录/我拿到了/等于证明」类第一人称复盘与口语表达（2026-09-22 用户定论）。

操作要点：「可能拿到」「不能直接」等书面表达不算口语；禁「全面提升」「显著」类空词；收尾跑 `scripts/check_style.py` 词表校验，新增/改写文件三段（漏洞描述/危害/利用方式）零第一人称零口语残留。

## 8. 请求/响应块保真

利用方式中的 HTTP 请求块必须完整携带 raw 证据里的鉴权头（Authorization/自定义 token 头）与 Content-Type，不做最小化裁剪，保证照抄代码块可直接重放（2026-09-08 因最小化请求块导致重放 415 后确立）；authKey/jwttoken/enterpriseInfo 等长鉴权值禁止手工转录，必须用脚本从源文件正则提取替换，写完逐字节比对（2026-09-10 某报告三处长值手工转录各缺 1-4 字符，脚本比对发现后修正）。每个请求块之后跟对应响应块（2026-09-29 用户要求确立）：响应内容从源报告回包段或任务根 dig 原始留存逐字节搬运，含状态行、留存全部响应头与响应体，不虚构状态码、响应头或响应体；留存仅部分字段时有什么写什么，缺失部分如实标注；请求-响应留存均无时在请求块后一行括注「（该请求的原始响应未留存…）」并指向正文依据；长响应体超约 40 行截断并标注截取范围；源报告回包段更新（如重放后）时 vault 同步搬运并复核样例与鉴权值一致（判例：2026-09-29 某定位系统 6 份补响应块，含 token 更新与样例同步）。

操作要点：源报告只有一行式请求（如裸 `GET /path?x=1`）时，URL 部分必须与源逐字节一致，可补齐 ` HTTP/1.1` 请求行结尾与标准头（Host/Accept/Accept-Language/Accept-Encoding/User-Agent/Referer/Connection）成完整块；匿名请求无鉴权头属正常，不要发明。响应块同理不发明：留存里没有的响应头不写，状态行 reason 未留存时只写状态码。

## 9. 增量同步

对比本 manifest 的 source_sha256，源未变即跳过；无漏洞/重复/排除（excluded）判定 hash 未变不重检；vault 文件 hash 与记录不符（被手工改过）时不覆盖，进裁决清单；模糊文档标待裁决不自动判 no-vuln；手动喊「全量重扫 SRC 报告」时忽略 no-vuln/duplicate/excluded 缓存全部重检。

操作要点：普通轮次靠 hash 缓存省力；「全量重扫」是显式口令，触发后连 no-vuln/duplicate/excluded 也要重新过收录判定。

## 10. 证据文件

报告目录内的 raw证据/、assets/ 等非报告文件记 ignore，hash 缓存不再判定；其内容按源报告引用关系呈现在漏洞文件中。

操作要点：ignore 条目仍记 source_sha256 供变更检测，只是不参与收录判定。

## 11. 证伪项剔除

源报告中的对照组、已证伪项、已防御面等阴性结果清单不录入 vault 文件（如「不构成漏洞」「上传面已防御」类条目）；利用链内部用于差分证明的阴性对照（假 token 被拒、错误口令被拒等）保留。

操作要点：分界线=是否属于本漏洞的证明链。WAF 逐词放行/拦截边界、不存在的用户名回「操作失败」的对照包、密码策略分支验证，都是差分证明，保留；「以下面已防御，不构成漏洞」式独立清单，剔除。

## 12. 重复漏洞判定

判定维度为根因+受影响接口+数据对象。同一根因的组件级缺陷多个实例（如 OnlineDev 列表越权命中不同业务表）合并为一条 vault 文件，manifest 记多个 imported 条目指向同一 vault_file；同一系统不同接口、不同修复点的相似发现各自成条并在正文互链（2026-09-08 某访客系统四报告审查确立）。

操作要点：查重先按 host、单位名、接口名、漏洞类型关键词 grep manifest entries 与 vault；同名不同系统不算重复（判例：某市学校体育场馆预约平台 vs 某市体育场馆智能管理系统，名称相近但不同单位不同系统不同根因）。同单位第二洞在 manifest note 标注「同单位第二洞」，正文可用「**关联发现**」行互链。

## 13. 源删除处理

源文件从报告目录消失时，manifest 条目改判 source-deleted 并移除 vault 引用，对应 vault 文件随之删除；删除前先确认其内容是否已被其余源报告吸收（如导出链并入其它报告），未被覆盖的独有内容在当轮整理报告中列明提醒用户确认（2026-09-08 访客小程序报告删除事件确立）。

操作要点：历史 source-deleted 条目在后续扫描中仍会出现在「消失」类，属既定状态不算新变化。vault 删除而源仍在= vault-deleted 待裁决态（判例：2026-09-18 某访客系统列表接口，通用型情报存档于 manifest 历史 note），不要自动重建。

## 14. 总览更新纪律

MOC 位于 vault 根 `SRC报告/00-总览.md`（2026-09-22 由 `2026-SRC/00-总览.md` 上移，涵盖 2026-SRC 与 ET-Pentest，按实际目录分区，行链接用 `[[完整路径\|显示名]]` 防同名漏洞跨单位歧义，**表格行内竖线必须转义 `\|`**，裸 `|` 被表格按列边界解析导致链接在竖线处截断不闭合——2026-09-26 用户在 Obsidian 发现存量 144 条截断并全量修复，新增行一律用转义写法）；不做哈希保护，更新前必须先 Read 实际内容再合并，保留用户手工改动（2026-09-08 用户删过待办项）。

操作要点：新增单位区块插入按单位名 Unicode 码点排序定位（同前缀组内按下一字排序，如「X市*」组 → 「X市Y」按第三字 → 其它前缀）；统计行必须按 vault 实际目录复核（判例：2026-09-21 复核发现前一批次 4 份文件落了 vault 但总览缺行、来源子计数漂移 1，均以磁盘实数纠正）；同名单位跨分区去重计数（判例：某市第三人民医院）。

## 15. 来源分组（机制 + 部署实例）

**机制（通用）：** 源路径位于 pentest/<来源目录>/ 下的漏洞按来源目录名分组，vault 落 2026-SRC/<来源>/<单位>/<漏洞名>.md；frontmatter 与 manifest note 按部署实例约定；00-总览 单列来源分区并在统计行单独计数；单位归并、去重、模板等其余规则不变。新增来源线时：在本 skill 部署配置节登记「来源目录→分区名→frontmatter/note 约定」，并同步 manifest rules 本条增补。

**部署实例（见 SKILL.md 本机部署配置节登记，机制不因实例增减而变）：**

| 来源目录（产出线） | 分区 | frontmatter | note |
|---|---|---|---|
| `NtCert-ARL/`（ARL 流水线产出） | `Ntcert/` | 加 `来源: NtCert-ARL` + tags `Ntcert`（手工项目不写） | 「Ntcert 高危」「Ntcert 中危」等 |
| `yakit-pentest-ntcert/`（Ntcert 队列 Yakit 复测/深测线产出） | `Ntcert/`（同 Ntcert 分区） | 加 `来源: yakit-pentest-ntcert` + tags `Ntcert` | 与 Ntcert 同惯例 |
| `yakit-pentest/`（yakit 工具链产出） | `yakit/`（与 Ntcert/ 平级） | 不加来源字段 | 标 yakit |

操作要点：note 惯例格式「Ntcert 高危」「Ntcert 中危」，同单位第二洞追加「；同单位第二洞」。总览来源分区统计行单独计数（如「其中 Ntcert 来源 96 个」）；yakit 分区排在手工单位索引之后、Ntcert 分区之前；同名单位跨分区不合并目录，总览计数按名称去重。（Ntcert 2026-09-10、yakit 2026-09-19、yakit-pentest-ntcert 2026-10-13 确立）

## 16. 黑灰产与暗链标注

源报告描述站点存在黑灰产内容（赌、黄、诈骗、私彩、博彩引流等）或暗链（隐藏外链、寄生页、暗跳转、被挂黑链）的漏洞，vault frontmatter tags 必须加「黑灰产」或「暗链」标签，漏洞名称保留标注字样，按源报告严重定级收录，00-总览 行内标注；挖洞侧规则同步于挖洞侧报告格式规则「黑灰产/暗链」条（2026-09-12 用户定论）。

操作要点：单位目录名加【黑灰产】前缀（历史判例域名见 manifest note）。定级以 manifest 现文为准（现文为「按源报告严重定级收录」）；若 manifest 改为上调口径，以改后现文执行。
